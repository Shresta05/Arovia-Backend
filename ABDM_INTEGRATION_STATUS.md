# AROVIA – FHIR / ABDM / HIS-EMR Integration Status

## 1. FHIR Resource Mapping

Status: LIVE

AROVIA maps patient data into these FHIR resources:

- Patient
- Condition
- Observation
- Medication
- AllergyIntolerance
- DiagnosticReport
- Encounter

The resources are generated by AROVIA API endpoints from the project's Supabase data.

---

## 2. FHIR Payload Validation

Status: LIVE

AROVIA validates FHIR resources before they are accepted for exchange.

Validation checks include:

- resourceType
- resource ID
- Patient references
- required fields for supported FHIR resources
- resource-specific required fields

Validation endpoint:

/api/fhir/validate

---

## 3. ABDM Identity / Linking Architecture

Status: MOCK / DEMO

AROVIA contains an ABDM identity-linking architecture using:

- AROVIA Patient ID
- Mock ABHA Number
- Mock ABHA Address
- Link status
- Identity source
- Link timestamp

Database table:

abdm_identity_links

Endpoint:

/api/abdm/link

No real ABDM network connection or real ABHA verification is performed.

---

## 4. ABDM Sandbox / Mock Flow

Status: MOCK / DEMO

Endpoint:

/api/abdm/mock

The mock flow simulates:

1. Patient identification
2. ABDM identity lookup
3. Mock authentication/session creation
4. ABDM identity confirmation
5. FHIR exchange readiness

No real ABDM authentication or health-record exchange occurs.

---

## 5. HIS / EMR Integration

Status: MOCK / DEMO

Endpoint:

/api/his-emr

The endpoint:

1. Checks patient consent.
2. Validates FHIR resources.
3. Simulates HIS/EMR acceptance.
4. Returns a mock transaction ID.

No real hospital, HIS, or EMR system is contacted.

---

## 6. Consent Management

Status: LIVE WITHIN AROVIA DEMO

AROVIA checks patient consent before allowing external HIS/EMR sharing.

The consent system stores:

- Patient ID
- Consent type
- Consent status
- Purpose
- Record type
- Granted date
- Expiry date
- Revocation date

The HIS/EMR API rejects sharing when consent is missing, not granted, or expired.

---
